# 架构说明

本文说明「智能烹饪助手」的整体结构、关键链路与扩展方式。面向需要修改代码或排查问题的开发者。

---

## 1. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│                        浏览器（React SPA）                    │
│  ChatPane / VideoPane / CookingStepsPanel / DangerAlarmOverlay│
│  hooks: useChatEngine · useVoiceOrchestration · useTTS        │
│  lib: ws.ts · audio-playback.ts · wakeword-stt.ts · voice/    │
└───────────────┬──────────────────────────────┬───────────────┘
                │ WebSocket /ws                │ 直连（唤醒/ASR）
                │ HTTP（/config /temperature…）│
┌───────────────▼──────────────────────────────┼───────────────┐
│                  FastAPI 后端 :8010           │               │
│  main.py（HTTP 路由 + WS 入口）                │               │
│  ws/router.py（事件表）                         │               │
│  ws/llm_handler.py（对话主链路）                │               │
│  ws_handlers/cooking.py（做饭状态机）           │               │
│  providers/（VLM · STT · TTS 适配层）           │               │
│  session.py（会话状态）· context_engine/（上下文）│              │
└───┬───────────────┬───────────────┬───────────┼───────────────┘
    │               │               │           │
    ▼               ▼               ▼           ▼
 云模型 API      USB 摄像头      串口硬件     香橙派 RK3588
 (VLM/STT/TTS)  (OpenCV)    (称重/红外/电磁阀)  KWS:8767 ASR:8768
                                               TTS:8769 推流/传感器
```

**三种运行形态**

| 角色 | 位置 | 职责 |
| --- | --- | --- |
| 后端 | 演示机 `:8010` | 全部业务逻辑、模型调用、硬件串口独占 |
| 前端 | 浏览器 `:5179` | 交互与展示；音频采集/播放；端侧语音直连 |
| 边缘端 | 香橙派 `RK3588` | 唤醒词、流式 ASR、端侧 TTS、摄像头推流、传感器采集 |

> 关键约束：**串口（称重 / 红外 / 电磁阀）由后端进程独占**，其他组件一律通过 HTTP 访问，不得自行打开串口。

## 2. 后端分层

### 2.1 入口与配置

- `app/main.py`：FastAPI 应用，注册全部 HTTP 路由与 WebSocket 入口（`/ws` 及若干设备专用 WS）。
- `app/config.py`：`Settings`（pydantic）唯一配置源，全部字段由环境变量驱动（`.env.local` → `os.environ`）。
  - 模块级单例 `settings`
  - `persist_env_value()`：**唯一的 env 写回通道**，只更新已有键，不删文件。

### 2.2 WebSocket 网关

`app/ws/router.py` 用一张 `EVENT_HANDLERS` 表把 `type` 映射到处理函数：

```
hello / user_text / audio_chunk / audio_end / audio_stream / audio_stream_end
interrupt / control / tts_test / tts_speak / timer_tts
video_frame / cooking
```

- 所有下行消息统一走 `ws_send(ws, type, payload)`，对 `ws=None` 有防御。
- 连接注册表在 `app/ws/connection.py` 的 `SESSION_CONNECTIONS`，支持跨会话广播（例如油温报警）。

### 2.3 对话主链路（重要）

`app/ws/llm_handler.py` 的 `_start_user_text_task` 是**所有文字的入口**，路由顺序不可随意调整：

```
用户文本
  ├─ 1. 倒计时类指令            → timer_manager
  ├─ 2. 烟雾/油烟类问句          → 场景快答
  ├─ 3. 显式下料指令            → parse_dispense_command（整句严匹配）
  ├─ 4. 盐量脉冲链路            → 秤重计算 → 锅铲确认门 → 1s 脉冲
  ├─ 5. 油温问句                → 结合当前菜谱步骤快答
  ├─ 6. 温度查询（确定性快答）   → 传感器实测，不走 LLM
  ├─ 7. 做饭状态机              → handle_cooking_user_text()
  ├─ 8. 场景响应                → handle_scene_response
  └─ 9. 普通 LLM 问答           → 上下文 + 工具调用
```

设计原则：**确定性优先**。能用规则/传感器确定回答的，不交给模型，避免幻觉与延迟。

### 2.4 做饭状态机

- 状态定义在 `app/session.py` 的 `SessionState.cooking_state`：
  ```
  IDLE → COLLECTING_INGREDIENTS / RECOMMENDING → AWAITING_SERVINGS
       → COOKING / STEP_WAITING → FINISHED
  ```
- 业务逻辑集中在 `app/ws_handlers/cooking.py`（`control_*` 动作函数 + 分支路由）。
- 通用能力在 `app/cooking_core.py`：
  - 关键词表、确认词分级匹配（`matches_cooking_confirmation`）
  - 菜谱查找 / 远程生成 / 份数计算
  - `send_cooking_text_with_tts`、`_collect_llm_text`
- 多个 `awaiting_*` 标志表示"正在等待用户确认"（份数、退出、步骤引导、食材备齐、盐量脉冲…）。
- **AI 意图兜底** `_ai_intent_fallback`：关键词全部未命中时用轻量 LLM 分类（只分类不执行），由 `AI_INTENT_FALLBACK_ENABLED` 控制。

### 2.5 Provider 适配层

`app/providers/` 把各家模型 API 收敛成统一接口：

```
base.py              TTSProvider 抽象 + downscale_jpeg_bytes()（图片 2048 限制统一缩放）
unified.py           统一 OpenAI 兼容协议实现
registry.py          供应商注册与元数据
modelscope/dashscope/deepseek/zhipu/sensenova/siliconflow ...   各平台适配
stt/ tts/            语音识别与合成（含 qwen3_asr_realtime、xiaomi_tts、dashscope_tts、tts_failover）
```

**重要设计：文字与视觉统一走 VLM 端点**——没有独立 LLM provider，`runtime.llm is runtime.vlm`。

`app/runtime_providers.py` 按 `settings` 构建运行时：`build_vlm_runtime` / `build_stt_runtime` / `build_tts_runtime`。

**所有带图请求入口必须经过 `downscale_jpeg_bytes()`**：平台对图片有 2048×2048 硬限制，而 USB 摄像头原生 2560×1440，超限会 400。

### 2.6 感知与安全

| 模块 | 职责 |
| --- | --- |
| `vision_handler.py` | 视觉帧分析，危险检测编排 |
| `hazard_rules.py` | 危险分类规则（明火 / 烟雾 / 油烟） |
| `safety_aggregator.py` | 多帧时序聚合，抑制单帧误报 |
| `oil_watch.py` | 油温监测与超温报警 |
| `usb_camera.py` | 本机 USB 摄像头常驻捕获，MJPEG 出流 |
| `remote_camera.py` / `remote_ir.py` / `remote_sensors.py` | 香橙派侧数据接入 |
| `camera_rotate.py` | 画面旋转（按侧独立） |

**油温链路**（`oil_watch.py`）：

- 常驻监控，每秒采样锅面最高温，数据需新鲜（超时视为无效）
- 达到目标温度**连续 3 次**采样才提醒（防抖）
- **超温报警**：锅面 ≥ 200°C 连续 3 次 → `danger_detected` 弹窗 + 语音，**60s 冷却**
- 监测超时 300s

### 2.7 执行器（硬件控制）

| 模块 | 说明 |
| --- | --- |
| `valve.py` | 电磁阀控制（串口通道、开合） |
| `dispense.py` | 下料状态机：按克数闭环，达标断电 |
| `fan.py` | 排气扇（小米插座，经 python-miio） |
| `temperature.py` / `weight.py` | 传感器读数与解析 |
| `device_controller.py` | 统一设备控制入口 |

**下料闭环要点**：轮询 0.5s，用未平滑的 `raw` 值判定达标（EMA 滞后会导致过冲），并留断电提前量补偿管路余料。

### 2.8 上下文与会话

- `app/context_engine/`：历史压缩（`compressor.py`）、历史管理（`history_manager.py`）、
  向量召回（`vector_store.py`，超出压缩窗口时按语义召回早期轮次）。
- `app/session.py`：`SessionState` 保存每会话的模型、语音、视觉、做饭状态。
- `app/timer_manager.py`：倒计时，**按 `session_id` 分桶**，避免多端互相串台。

### 2.9 菜谱服务

`app/services/recipe_service.py` 读取 `buzhou/HowToCook/dishes/` 下的 Markdown 菜谱：

- 解析菜名、难度、食材、步骤、小贴士、份量
- `search_by_name`：**同义词归一**（番茄=西红柿）+ `difflib` 模糊兜底
- `search_by_ingredients`：按食材搜索
- 进程内单例（`get_recipe_service()`）

### 2.10 MCP Server

`backend/mcp_server.py` 以 **stdio** 传输暴露工具，本质是后端的 HTTP 代理：

- 不开串口、不 import 后端 app（避免与后端争抢串口）
- 工具覆盖：温度、重量、去皮、下料、风扇、菜谱
- 客户端配置见根目录 `MCP使用说明.md`

## 3. 前端架构

### 3.1 数据流

```
WebSocket（lib/ws.ts）
   ↓ 分发表
useChatEngine（消息路由 / 聊天流 / 会话）
   ├→ useCookingMode       做饭状态镜像
   ├→ useTTS + audio-playback   PCM 播放队列
   ├→ useVoiceOrchestration 唤醒词与语音编排
   └→ useModelConfig       模型选择 + /config 同步
```

### 3.2 关键模块

| 文件 | 职责 |
| --- | --- |
| `lib/ws.ts` | WebSocket 封装、重连、事件分发 |
| `hooks/useChatEngine.ts` | **WS 消息分发表**、流式气泡、危险警报、打断 |
| `hooks/useVoiceOrchestration.ts` | 唤醒词监听、录音分段、端侧 ASR 直连 |
| `lib/wakeword-stt.ts` | 唤醒 + 持续识别控制器（含 VAD、回声门控） |
| `lib/voice/vad.ts` | 内联 VAD 与**回声门控**（AI 播报期间抑制自问自答） |
| `lib/audio-playback.ts` | PCM 队列、插播挂起/续播、墓碑防残块 |
| `hooks/useModelConfig.ts` | provider/model 选择，`/config` 双向同步 |
| `components/DangerAlarmOverlay.tsx` | 危险警报大弹窗 + 警笛 |

### 3.3 音频链路

- 后端 TTS 输出 **PCM** 分块下发，前端入队播放
- 队列有容量上限，超限丢弃并告警（避免无界增长）
- AI 播报期间：`EchoGate` 提高打断门限，避免扬声器回采被识别为用户说话

### 3.4 端侧语音

香橙派 KWS / ASR 由**前端直连**（不经后端）：

```
ws://<pi>:8767/kws   唤醒词
ws://<pi>:8768/asr   流式识别
```

> 给这两个连接加客户端功能前，**必须先确认服务端消息协议**（曾因向二进制 PCM 服务端发送 JSON ping 导致连接死亡循环）。

## 4. 边缘端架构（香橙派 RK3588）

```
systemd 服务
  opi-camera     摄像头推流客户端      → 后端 /ws/opi-cam
  opi-ir         MLX90640 红外客户端    → 后端 /ws/opi-ir
  opi-sensors    称重 + 双电磁阀客户端  → 后端 /ws/opi-sensors
  tts-sambert    端侧 TTS :8769         ← 前端 / 后端调用
Docker 容器
  rokid-kws      唤醒词 :8767
  rokid-asr      流式 ASR :8768
```

**串口自动分类**：现场 4 个 CH340 设备（称重 / 电磁阀1 / 电磁阀2 / 红外），断电重插后
`ttyUSB` 编号会洗牌，因此客户端按**应答特征**识别设备，而非固定编号。

双阀的通道 ↔ 物理口绑定表在 Pi 的 `.valve_channels.json`，删除即可重新分配。

## 5. 关键设计取舍

1. **确定性优先于模型**：温度、重量、油温、显式下料指令都由规则或传感器直接回答，LLM 只处理开放问答。
2. **单一配置源**：所有可调参数集中在 `Settings`，避免散落的硬编码；写回只走 `persist_env_value()`。
3. **Provider 收敛**：文字与视觉统一到 VLM 端点，减少一套 provider 维护成本。
4. **串口独占**：后端是唯一打开串口的进程，MCP / 前端一律走 HTTP。
5. **快照式公开仓库**：对外仓库为独立历史快照，不含内部提交历史与密钥。

## 6. 常见改动指引

### 新增一个模型供应商

1. `app/providers/` 下新增适配类（通常继承 `unified.py` 的 OpenAI 兼容实现）
2. 在 `registry.py` 注册元数据
3. `app/runtime_providers.py` 增加构建分支
4. 前端 `ModelSelector/constants.ts` 增加图标与预设模型
5. 如需持久化 Key，确认 `PROVIDER_ENV_PREFIX` 映射存在

### 新增一个 WS 事件

1. 前端 `lib/ws.ts` / `hooks/useChatEngine.ts` 发送与分发
2. 后端 `app/ws/router.py` 的 `EVENT_HANDLERS` 注册
3. 处理函数放在对应 `ws_handlers/` 模块

### 新增一个硬件设备

1. 后端新增模块（串口操作必须在后端）
2. `app/main.py` 暴露 HTTP 端点
3. 需要时在 `llm_tools.py` 增加只读工具，让模型能"问到"实测数据
4. 前端新增状态展示组件

## 7. 排查建议

| 问题 | 首先看 |
| --- | --- |
| 后端起不来 | `backend/data/backend_uvicorn.*.err.log` |
| 业务链路异常 | `logs/backend/<日期>.md` 结构化日志 |
| 前端无画面 | `/usb-camera/status`、后端日志摄像头模块 |
| 语音无响应 | 浏览器控制台 + 端侧 KWS/ASR 连接状态 |
| 模型 400 | 检查图片尺寸是否已过 `downscale_jpeg_bytes` |
| 测试基线 | `pytest tests/ -q`（大量 skipped 通常表示后端未启动） |
